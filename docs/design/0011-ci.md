## 0. Result

```
make ci        52 s   from an empty venv on Python 3.12

  checks   lint · 8 import contracts · mypy(platform) · OpenAPI 149/149 · 313 unit tests
  tests    760 tests under -n 4 · migrations round trip · 8 database invariants
```

Two jobs, run in parallel. `.github/workflows/ci.yml` contains no commands of its
own — every step is a `make` target, so a failing pipeline is reproducible with
one command and there is no second place for the real build to live.

**The pipeline found six defects on its first clean run.** Five of them are
things the existing 755-test suite could never have found, because it had never
been executed against a clean install of the declared Python.

---

## 1. `pip install -e .` had never worked

`make install` is CI's first step. It failed immediately:

```
error: Multiple top-level packages discovered in a flat-layout: ['app', 'docs',
'tests', 'scripts', 'openapi', 'registry', 'migrations'].
```

There was no `[build-system]` section and no package discovery config. Nothing
had noticed because `python3 -m pytest` from the repository root puts the root on
`sys.path`, so the package was never actually *installed* — only ever imported
in place.

That is not a packaging nicety. It is the reason the next four items existed:
**there was no environment in which the declared dependency list was the actual
dependency list.**

## 2. Four defects that only a clean install could surface

### 2.1 `cryptography` was never declared, and the competition lobby needs it

```python
# app/api/routers/competitions.py
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
```

Not in `dependencies`. It worked locally because something else pulled it in
transitively. On a fresh deploy `GET /competitions/{xid}/lobby` returns **500**,
and the synchronized-start feature — the thing that makes a competition a
contest rather than a shared homework link — does not work at all.

Three tests failed with `ModuleNotFoundError` the first time the suite ran in a
clean environment. They had passed on every previous run.

### 2.2 Every id this project has ever minted was a uuid4

```python
try:
    from uuid6 import uuid7 as _uuid7
except ImportError:  # pragma: no cover - dev convenience only
    _uuid7 = None

def new_xid(): return _uuid7() if _uuid7 is not None else uuid.uuid4()
```

`uuid6` was not installed in the development environment. It never had been. So
the fallback fired on **every id in every test run for the life of the project**,
and nothing said so — a uuid4 is a perfectly good opaque identifier, and opacity
was the only property anything checked.

What was silently discarded is the reason `ids.py` exists. UUIDv7 puts a
millisecond timestamp in its leading bits so consecutive inserts land next to
each other in the index instead of scattering across it. At a few thousand rows
that is invisible. At the 20-50k users this design is supposed to reach without a
rewrite, it is the difference between an index that stays in cache and one that
does not — and the ids are in the database by then, so it is not reversible.

The import is now hard. A missing declared dependency should fail at startup the
same way a worker without ffmpeg does, rather than quietly delivering a system
that is subtly worse forever. `tests/platform/test_ids.py` asserts version 7 and
creation-order sorting; both fail against the old fallback, which is how they
were checked.

### 2.3 A ruff upgrade would have turned the lint gate red

The repository had no `[tool.ruff.lint]` section, so the gate meant "whatever
this version of ruff defaults to". Between the locally installed 0.15.8 and the
0.16.0 a fresh `pip install` fetches:

```
ruff 0.15.8   →  0 findings
ruff 0.16.0   →  441 findings
```

325 of them were `B008`, *function call in default argument* — which flags
`Depends()`, `Query()` and `Body()`, i.e. every FastAPI handler ever written. An
unpinned rule set means the build's verdict depends on which day the runner
installed its tools.

The set is now explicit. `B` (bugbear) is included, minus `B008`, because it cost
five fixes and three of them were the failure mode this project keeps hitting:

| | |
|---|---|
| `B905` ×2 | `zip()` without `strict=` — silently pairs to the shorter list |
| `B017` | `pytest.raises(Exception)` — satisfied by a `TypeError` from a signature change |
| `B904` | `raise` inside `except` without `from`, losing the cause |
| `B007` | unused loop variable |

`I` (import sorting) is not on: it wants 31 files reordered, which is a mechanical
change that does not belong in the commit that turns CI on. It is the obvious
next ratchet and `ruff check --select I --fix` is the whole job.

### 2.4 The `zip()` finding was real, and my first fix was wrong

`B905` flagged two helpers pairing questions with answers. I added `strict=True`,
which failed seven tests — the call sites pass one answer for a three-item paper
**on purpose**, because a partial autosave is the thing under test.

The rule was still right: the call was ambiguous about which list was allowed to
be short. The fix is to index by the answer list, which says "answer the first N
questions" outright and raises if the answers outnumber the paper.

## 3. In CI, a skip is a failure

This is the load-bearing decision, and it is `0010` §3.2 applied forward. That
document records `pytest -n 4` printing **"355 passed, 400 skipped"** and exiting
**0** — more than half the suite unexecuted, reported as success.

The fix there removed one `except: pytest.skip(...)`. This closes the category:

```python
# tests/conftest.py
@pytest.hookimpl(wrapper=True, trylast=True)
def pytest_runtest_makereport(item, call):
    ...  # under CI, report.outcome = "failed"
```

A skip is the right answer on a laptop with no PostgreSQL and no ffmpeg — the 313
pure domain tests still run and still mean something. It is the wrong answer on a
runner whose entire job is to provide those dependencies.

The switch is the `CI` environment variable rather than a flag of our own,
because every CI provider sets it and nothing else does, so the gate cannot be
lost when someone edits a workflow file. `ALLOW_SKIPS=1` overrides it.

It is deliberately blunt: it does not enumerate the skips it knows about, it
forbids the category. A skip added in a year for a reason nobody remembers fails
CI until somebody states why. `xfail` is untouched — an expected failure is a
recorded fact, not an unexecuted test.

Verified by hiding `ffmpeg` and `ffprobe`:

| | laptop | CI |
|---|---|---|
| ffmpeg present | 35 passed | 35 passed |
| ffmpeg absent | 22 passed, 13 skipped | 22 passed, **13 errors**, exit 1 |

That test also found that the `wav` fixture's guard was on two classes rather
than on the fixture, so two tests in `TestResumableUpload` **errored** on a
machine without ffmpeg against a README promising they skip cleanly. The guard is
on the fixture now, where the next test to need a wav cannot forget it.

## 4. What each job gates, and why it is that job

**`checks`** — no service containers, so it starts instantly. A lint error should
not wait three minutes behind a PostgreSQL image pull. Ruff, the eight import
contracts, mypy on the kernel, the OpenAPI document and route coverage, and the
313 database-free tests.

**`tests`** — `postgres:16` plus ffmpeg.

- `make test-fast` — 760 tests under `-n 4`, ~33 s.
- `make migrations` — `upgrade head → downgrade base → upgrade head` on a scratch
  database, plus an assertion that the history has exactly one head. The middle
  step is the one that finds things; `downgrade` rots quietly, and the day it is
  needed is the day a deploy is already going badly. Verified by breaking a
  `DROP TABLE` and watching it fail.
- `make invariants` — see §6.

Both pin **Python 3.12**, the floor `pyproject.toml` declares and which nothing
had ever tested; development happened on 3.11.

The `tests` job proves its environment before running anything — Python ≥ 3.12,
ffmpeg and ffprobe present, PostgreSQL reachable, **and the role is superuser**.
That last one is not decoration: the per-test reset needs
`SET session_replication_role = replica` to clear `audit_log` and
`item_exposures`, whose append-only triggers exist precisely to stop that. A
non-superuser role turns into 400 confusing failures; the check turns it into one
sentence.

## 5. mypy is gated on one package, not on the codebase

```
mypy <package> --ignore-missing-imports

app/platform      0 errors   ← gated
app/modules      22
app/workers      22
app/api          80
```

`mypy` has been a declared dev dependency since the first commit and had never
been run. Introducing a type checker across a finished codebase is its own piece
of work; bolting it onto the commit that turns CI on would mean shipping a
pipeline that is red on day one, and a red pipeline nobody can fix is a pipeline
everybody learns to ignore.

So it gates `app/platform` — the kernel every other layer depends on, and clean
today. It can only go up from there, one package at a time, and the layering
contracts mean the order is already decided: `platform`, then `modules`, then the
two composition roots.

This is also where mypy earned its place. On the newer version a clean install
fetches, it found §2.2 — the uuid4 fallback — as an assignment type error.

## 6. The invariants script could not fail

`scripts/verify_invariants.sql` proves the promises in `0002-data-model.md` §10
are enforced by PostgreSQL rather than by application code a future handler can
forget: append-only audit log, one current answer key per question version, a
published test version is immutable, submitted answers are frozen, content
defaults to org-private. These are the contractual ones — a centre's material not
leaking, a regrade being auditable.

It ran with `ON_ERROR_STOP off`, and a correct run is *full of* errors, because
each error IS an invariant firing. Its exit code meant nothing, which is why it
had never been in CI.

Two changes make it a gate:

**It needed a transaction.** Every `SAVEPOINT` in it raised *"can only be used in
transaction blocks"* — psql was in autocommit, so the savepoints did nothing and
the script only appeared to work because each failing statement was its own
transaction that rolled itself back. It emitted nine spurious errors of its own,
which is exactly why the output could never be machine-checked. One `BEGIN`.

**`scripts/check_invariants.py` gives it a verdict.** Every expected refusal must
fire, every reported value must match, and *nothing else may error* — an
unexpected error means the fixtures no longer apply cleanly, and then every check
after it is measuring something other than what it claims. It then runs
`acceptance_new_question_type.py` against the same database.

Verified by removing `UPDATE` from the audit-log trigger:

```
FAIL  invariant NOT enforced: audit log is append-only (UPDATE and DELETE)
      — expected 2 refusal(s) matching 'is append-only', saw 1
```

The first version reported that as *"(DELETE) not enforced"* while the sabotage
was on UPDATE, because both raise the same message and the matcher consumed the
first error it found. A true failure with a false cause is how a regression gets
chased in the wrong file, so the two are one entry with a count.

Two things in the same script were also strengthened while it was being made
gateable: expected values that embed a date are **computed**, not pinned — a
literal `minor=true` would pass for eighteen months and then fail on 2028-03-01
with no code change, which is the same shape as the test that only failed after
22:00 in `0010` §3.1. And `acceptance_new_question_type.py` asserted the schema
fingerprint was unchanged but never that the question **scored correctly**, so it
would have printed PASS on a new question type that graded every answer wrong.

## 7. Cost

Two jobs, roughly 2 and 5 minutes, on a 2,000-minute monthly free allowance.
Under $0 at this volume, which matters given the <$50/month infrastructure budget.

It runs on every push, because this repository has no pull-request habit — work
goes straight to a branch, and a gate that only fires on PRs would never fire. A
branch that also has an open PR therefore runs twice; when that stops being an
acceptable ~6 minutes, the fix is to narrow `push` to `[main]`, one line.

`concurrency: cancel-in-progress` kills superseded runs. Nothing is learned from
finishing a run against a commit that is already history.

## 8. Still open

1. **Actions are pinned by major tag, not by commit SHA.** `actions/checkout@v4`
   is a moving reference; the hardening is to pin the 40-character SHA. Worth
   doing, and worth doing by reading the SHAs off GitHub rather than from
   memory — a wrong SHA is a pipeline that cannot start.

2. **No MinIO service, so `S3Storage` is still untested.** `0009` §7 called this
   out and CI is where it gets fixed: a `minio/minio` service container is a
   dozen lines, and it costs contributors nothing because it runs in CI rather
   than on their laptops. The first real S3 deploy is currently the first real
   test of that class.

3. **No coverage measurement.** `pytest-cov` is installed and never used. I would
   rather have no number than a number that becomes a target, but "which
   `app/api/routers` lines are unexecuted" is a genuinely useful question and it
   is one flag away.

4. **Nothing checks the workers actually start.** The suite tests actors as
   functions and `test_actors.py` covers the routing table, but no CI step boots
   `dramatiq app.workers.actors` against a real Redis. The broker-binding bug in
   `0008` — actors silently bound to the wrong Redis because `@dramatiq.actor`
   resolves the broker at decoration time — was found by running real processes
   and is invisible to every test in the suite. A Redis service and a
   thirty-second smoke run would cover it.

5. **Import sorting is off**, as above: 31 files, one `--fix`.

6. **The suite emits 668 warnings** and CI reads none of them. Among them is
   `InsecureKeyLengthWarning: The HMAC key is 18 bytes long, below the minimum
   recommended 32` — from the test JWT secret, so harmless here, but exactly the
   kind of thing that should be `-W error` for a chosen list rather than scrolled
   past. A deprecation that is a warning today is a failure on some future
   dependency bump, and finding out at upgrade time is finding out late.

7. **No dependency update automation and no upper bounds.** Every dependency is
   `>=`, so a clean install fetches whatever is newest — which is how §2.3
   happened, and it will happen again with a different package. Dependabot on a
   weekly schedule turns that from a surprise into a pull request.
