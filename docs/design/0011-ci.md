## 0. Result

```
make ci        2 m 10 s   from an empty venv on Python 3.12

  checks     6 s   lint · 8 import contracts · mypy(platform) · OpenAPI 149/149
                   · 383 unit tests
  tests   2 m 03 s 1382 tests under -n 4 · per-path coverage floors · migrations
                   round trip · 8 database invariants · a real worker process over
                   a real Redis · S3Storage against MinIO
```

The two jobs run in parallel on GitHub Actions, so the wall clock there is the
`tests` job plus image pull; `make ci` runs them in sequence, which is the figure
above. `.github/workflows/ci.yml` contains no commands of its own — every step is
a `make` target, so a failing pipeline is reproducible with one command and there
is no second place for the real build to live.

**The pipeline found six defects on its first clean run.** Five of them are
things the existing 755-test suite could never have found, because it had never
been executed against a clean install of the declared Python.

Measuring coverage then found nineteen more, across nine routers that were each
under 85% (§§10-18):

| | |
|---|---|
| `auth.py` | an authentication bypass — POST a phone number, get a session |
| `platform_ops.py` | an unauthenticated payment callback that marked any order paid |
| `assets.py` | the listening transcript, readable by any student at the centre |
| `identity.py` | a roster returning every member's phone number and minor flag |
| `speaking.py` | a safety-evidence upload that recorded audio it never stored |
| `competitions.py` | a capacity-capped contest that returned 500 on every entry, and a leaderboard that ignored the ranking it had computed |
| `tests_authoring.py` | a section move that 500'd one way and silently broke the exam the other, and a band map that could not be attached at all — so nothing could be published |
| `teaching.py` | a teacher refused permission to assign to their own centre's students, and a band-map regrade reporting an impact of zero |

In almost every case **the OpenAPI document already described the correct
behaviour and the implementation did something else.** That pattern is the
finding, and it is the argument for the per-path floors in §10: the uncovered part
of a router is not evenly distributed noise, it is the branch nobody ever needed
to make work.

## 1. `pip install -e .` had never worked

`make install` is CI's first step. It failed immediately:

```
error: Multiple top-level packages discovered in a flat-layout: ['app', 'docs',
'tests', 'scripts', 'openapi', 'registry', 'migrations'].
```

There was no `[build-system]` section and no package discovery config. Nothing
had noticed because `python3 -m pytest` from the repository root puts the root on
`sys.path`, so the package was never actually *installed* — only ever imported
in place.

That is not a packaging nicety. It is the reason the next four items existed:
**there was no environment in which the declared dependency list was the actual
dependency list.**

## 2. Four defects that only a clean install could surface

### 2.1 `cryptography` was never declared, and the competition lobby needs it

```python
# app/api/routers/competitions.py
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
```

Not in `dependencies`. It worked locally because something else pulled it in
transitively. On a fresh deploy `GET /competitions/{xid}/lobby` returns **500**,
and the synchronized-start feature — the thing that makes a competition a
contest rather than a shared homework link — does not work at all.

Three tests failed with `ModuleNotFoundError` the first time the suite ran in a
clean environment. They had passed on every previous run.

### 2.2 Every id this project has ever minted was a uuid4

```python
try:
    from uuid6 import uuid7 as _uuid7
except ImportError:  # pragma: no cover - dev convenience only
    _uuid7 = None

def new_xid(): return _uuid7() if _uuid7 is not None else uuid.uuid4()
```

`uuid6` was not installed in the development environment. It never had been. So
the fallback fired on **every id in every test run for the life of the project**,
and nothing said so — a uuid4 is a perfectly good opaque identifier, and opacity
was the only property anything checked.

What was silently discarded is the reason `ids.py` exists. UUIDv7 puts a
millisecond timestamp in its leading bits so consecutive inserts land next to
each other in the index instead of scattering across it. At a few thousand rows
that is invisible. At the 20-50k users this design is supposed to reach without a
rewrite, it is the difference between an index that stays in cache and one that
does not — and the ids are in the database by then, so it is not reversible.

The import is now hard. A missing declared dependency should fail at startup the
same way a worker without ffmpeg does, rather than quietly delivering a system
that is subtly worse forever. `tests/platform/test_ids.py` asserts version 7 and
creation-order sorting; both fail against the old fallback, which is how they
were checked.

### 2.3 A ruff upgrade would have turned the lint gate red

The repository had no `[tool.ruff.lint]` section, so the gate meant "whatever
this version of ruff defaults to". Between the locally installed 0.15.8 and the
0.16.0 a fresh `pip install` fetches:

```
ruff 0.15.8   →  0 findings
ruff 0.16.0   →  441 findings
```

325 of them were `B008`, *function call in default argument* — which flags
`Depends()`, `Query()` and `Body()`, i.e. every FastAPI handler ever written. An
unpinned rule set means the build's verdict depends on which day the runner
installed its tools.

The set is now explicit. `B` (bugbear) is included, minus `B008`, because it cost
five fixes and three of them were the failure mode this project keeps hitting:

| | |
|---|---|
| `B905` ×2 | `zip()` without `strict=` — silently pairs to the shorter list |
| `B017` | `pytest.raises(Exception)` — satisfied by a `TypeError` from a signature change |
| `B904` | `raise` inside `except` without `from`, losing the cause |
| `B007` | unused loop variable |

`I` (import sorting) is not on: it wants 31 files reordered, which is a mechanical
change that does not belong in the commit that turns CI on. It is the obvious
next ratchet and `ruff check --select I --fix` is the whole job.

### 2.4 The `zip()` finding was real, and my first fix was wrong

`B905` flagged two helpers pairing questions with answers. I added `strict=True`,
which failed seven tests — the call sites pass one answer for a three-item paper
**on purpose**, because a partial autosave is the thing under test.

The rule was still right: the call was ambiguous about which list was allowed to
be short. The fix is to index by the answer list, which says "answer the first N
questions" outright and raises if the answers outnumber the paper.

## 3. In CI, a skip is a failure

This is the load-bearing decision, and it is `0010` §3.2 applied forward. That
document records `pytest -n 4` printing **"355 passed, 400 skipped"** and exiting
**0** — more than half the suite unexecuted, reported as success.

The fix there removed one `except: pytest.skip(...)`. This closes the category:

```python
# tests/conftest.py
@pytest.hookimpl(wrapper=True, trylast=True)
def pytest_runtest_makereport(item, call):
    ...  # under CI, report.outcome = "failed"
```

A skip is the right answer on a laptop with no PostgreSQL and no ffmpeg — the 317
pure domain tests still run and still mean something. It is the wrong answer on a
runner whose entire job is to provide those dependencies.

The switch is the `CI` environment variable rather than a flag of our own,
because every CI provider sets it and nothing else does, so the gate cannot be
lost when someone edits a workflow file. `ALLOW_SKIPS=1` overrides it.

It is deliberately blunt: it does not enumerate the skips it knows about, it
forbids the category. A skip added in a year for a reason nobody remembers fails
CI until somebody states why. `xfail` is untouched — an expected failure is a
recorded fact, not an unexecuted test.

Verified by hiding `ffmpeg` and `ffprobe`:

| | laptop | CI |
|---|---|---|
| ffmpeg present | 35 passed | 35 passed |
| ffmpeg absent | 22 passed, 13 skipped | 22 passed, **13 errors**, exit 1 |

That test also found that the `wav` fixture's guard was on two classes rather
than on the fixture, so two tests in `TestResumableUpload` **errored** on a
machine without ffmpeg against a README promising they skip cleanly. The guard is
on the fixture now, where the next test to need a wav cannot forget it.

## 4. What each job gates, and why it is that job

**`checks`** — no service containers, so it starts instantly. A lint error should
not wait three minutes behind a PostgreSQL image pull. Ruff, the eight import
contracts, mypy on the kernel, the OpenAPI document and route coverage, and the
317 database-free tests.

**`tests`** — `postgres:16`, `redis:7`, `minio/minio`, and ffmpeg.

- `make coverage` — 1382 tests under `-n 4` plus the per-path floors, ~96 s. §10.
- `make migrations` — `upgrade head → downgrade base → upgrade head` on a scratch
  database, plus an assertion that the history has exactly one head. The middle
  step is the one that finds things; `downgrade` rots quietly, and the day it is
  needed is the day a deploy is already going badly. Verified by breaking a
  `DROP TABLE` and watching it fail.
- `make invariants` — see §6.
- `make smoke` — see §7.
- `S3Storage` against MinIO — see §9.

Both pin **Python 3.12**, the floor `pyproject.toml` declares and which nothing
had ever tested; development happened on 3.11.

The `tests` job proves its environment before running anything — Python ≥ 3.12,
ffmpeg and ffprobe present, PostgreSQL reachable, **and the role is superuser**.
That last one is not decoration: the per-test reset needs
`SET session_replication_role = replica` to clear `audit_log` and
`item_exposures`, whose append-only triggers exist precisely to stop that. A
non-superuser role turns into 400 confusing failures; the check turns it into one
sentence.

## 5. mypy is gated on one package, not on the codebase

```
mypy <package> --ignore-missing-imports

app/platform      0 errors   ← gated
app/modules      22
app/workers      22
app/api          80
```

`mypy` has been a declared dev dependency since the first commit and had never
been run. Introducing a type checker across a finished codebase is its own piece
of work; bolting it onto the commit that turns CI on would mean shipping a
pipeline that is red on day one, and a red pipeline nobody can fix is a pipeline
everybody learns to ignore.

So it gates `app/platform` — the kernel every other layer depends on, and clean
today. It can only go up from there, one package at a time, and the layering
contracts mean the order is already decided: `platform`, then `modules`, then the
two composition roots.

This is also where mypy earned its place. On the newer version a clean install
fetches, it found §2.2 — the uuid4 fallback — as an assignment type error.

## 6. The invariants script could not fail

`scripts/verify_invariants.sql` proves the promises in `0002-data-model.md` §10
are enforced by PostgreSQL rather than by application code a future handler can
forget: append-only audit log, one current answer key per question version, a
published test version is immutable, submitted answers are frozen, content
defaults to org-private. These are the contractual ones — a centre's material not
leaking, a regrade being auditable.

It ran with `ON_ERROR_STOP off`, and a correct run is *full of* errors, because
each error IS an invariant firing. Its exit code meant nothing, which is why it
had never been in CI.

Two changes make it a gate:

**It needed a transaction.** Every `SAVEPOINT` in it raised *"can only be used in
transaction blocks"* — psql was in autocommit, so the savepoints did nothing and
the script only appeared to work because each failing statement was its own
transaction that rolled itself back. It emitted nine spurious errors of its own,
which is exactly why the output could never be machine-checked. One `BEGIN`.

**`scripts/check_invariants.py` gives it a verdict.** Every expected refusal must
fire, every reported value must match, and *nothing else may error* — an
unexpected error means the fixtures no longer apply cleanly, and then every check
after it is measuring something other than what it claims. It then runs
`acceptance_new_question_type.py` against the same database.

Verified by removing `UPDATE` from the audit-log trigger:

```
FAIL  invariant NOT enforced: audit log is append-only (UPDATE and DELETE)
      — expected 2 refusal(s) matching 'is append-only', saw 1
```

The first version reported that as *"(DELETE) not enforced"* while the sabotage
was on UPDATE, because both raise the same message and the matcher consumed the
first error it found. A true failure with a false cause is how a regression gets
chased in the wrong file, so the two are one entry with a count.

Two things in the same script were also strengthened while it was being made
gateable: expected values that embed a date are **computed**, not pinned — a
literal `minor=true` would pass for eighteen months and then fail on 2028-03-01
with no code change, which is the same shape as the test that only failed after
22:00 in `0010` §3.1. And `acceptance_new_question_type.py` asserted the schema
fingerprint was unchanged but never that the question **scored correctly**, so it
would have printed PASS on a new question type that graded every answer wrong.

## 7. The one step that starts a second process

Every actor test in the suite calls the actor functions directly. That is the
right way to test them — the logic lives in `app/modules/*` — but it means
nothing in 760 tests can see the failure that actually happened during the worker
phase:

> `@dramatiq.actor` binds `dramatiq.get_broker()` **at decoration time**, and
> `get_broker()` invents a RedisBroker on `localhost:6379` when none is
> installed. Import `app.workers.actors` before `broker.configure()` and every
> actor is permanently bound to the wrong Redis. Nothing raises. The queue is
> simply empty.

The guard is one line — `broker.current()` above the first decorator in
`actors.py` — and anybody could reorder it. `make smoke` runs the real thing:
migrate a scratch database, spawn `dramatiq app.workers.actors` as a separate OS
process, drain an outbox row through the real `dispatch`, enqueue a job, and wait
for the row to change in PostgreSQL.

### 7.1 The obvious version of this test does not work

Delete `broker.current()` and the smoke test fails — but only because nothing is
listening on 6379. **With a Redis on the default port, the sabotaged build
passes.** Verified, not assumed: the enqueuer and the worker misbind *together*,
consistently, and the job flows perfectly through the wrong broker.

```
sabotaged, no decoy      ConnectionRefusedError, exit 1
sabotaged, decoy on 6379 PASS  outbox -> relay -> Redis -> worker -> PostgreSQL
```

That second line is the whole lesson. Whether the work happened tells you nothing
about *which broker did it*, so the test asks the configured Redis directly: a
correctly bound worker leaves `dramatiq:__heartbeats__` in it, a misbound one
leaves it empty. That holds whatever port CI picks, which beats depending on CI
to pick a non-default one.

The service is on 6380 anyway, so a misbinding now fails twice rather than once.

## 8. Cost

Two jobs, roughly 1 and 2 minutes, on a 2,000-minute monthly free allowance.
Under $0 at this volume, which matters given the <$50/month infrastructure budget.

It runs on every push, because this repository has no pull-request habit — work
goes straight to a branch, and a gate that only fires on PRs would never fire. A
branch that also has an open PR therefore runs twice; when that stops being an
acceptable ~6 minutes, the fix is to narrow `push` to `[main]`, one line.

`concurrency: cancel-in-progress` kills superseded runs. Nothing is learned from
finishing a run against a commit that is already history.

## 9. S3Storage, against a real MinIO

`S3Storage` was covered by a signature comparison and nothing else, so **the
first real S3 deploy would have been its first real test** — open since `0009`
§7. The gap was wider than it sounds: `FileStorage` implements multipart by
writing part files into a directory, which is not remotely how S3 behaves.
Minimum part sizes, ETags, `NoSuchUpload`, SigV4 query strings and path-style
addressing exist only on the S3 side.

### 10.1 The contract moved out of the local backend's test file

`tests/platform/test_storage.py` opened by saying it "tests the contract rather
than the implementation — every assertion here is one an S3 backend must also
satisfy", and then ran every one of them against `FileStorage` alone.

The contract now lives in `tests/storage_contract.py` and both backends subclass
it: the local one in the unit suite with no services, S3 in the integration suite
against MinIO. The one operation that cannot be shared is uploading a part —
deliberately absent from the port, because in production the client PUTs to a
presigned URL and the app server never sees the bytes. Each subclass supplies it,
and the S3 version really does PUT over HTTP. That path had never been exercised
by anything, despite being the mechanism behind Deliverable 3's promise that a
teacher's 40 MB WAV does not transit the app server.

### 10.2 Two divergences, found within a minute of the first run

Both are the same defect, and it is the one this module exists to prevent.

```python
# storage.py, line 1
"""Object storage. The ONLY place an S3 SDK appears (ADR-0001 §5.5)."""
```

`FileStorage.get` raised `StorageError` for a missing object. `S3Storage.get`
raised `botocore.errorfactory.NoSuchKey` — which no caller can catch without
importing botocore, which is precisely the dependency the port is there to
contain. Identical signatures, and the shape check was happy.

The second is worse, and it was in `stat`:

```python
try:
    head = self._client.head_object(Bucket=self.bucket, Key=key)
except Exception:
    return None
```

`stat() is None` means "no such object" and callers act on it —
`content/media.py` reads it as "the upload did not land" and marks the asset
failed. A refused connection, an expired credential, a 500 from the provider:
all of them returned None. **During an outage every object in the system would
have reported itself missing**, and the ingest path would have recorded data loss
that had not happened.

It now distinguishes a genuine 404 from everything else. Verified by pointing a
store at port 1 and watching `stat` raise instead of shrug, and by reverting the
narrowing and watching that test fail.

### 10.3 MinIO is a step, not a service

`services:` runs the image's default command and `minio/minio` needs `server
/data`, which there is no way to supply. So it is `docker run` plus a health
poll in a step — which also means a failure to start names itself, rather than
arriving as twenty-nine connection errors in the test output.

## 10. Coverage, without a number to game

87% overall when first measured, 96% now. That figure is **reported and not
enforced**, and the reasoning matters more than the number.

A single repository-wide percentage is the wrong gate. It rewards testing
whatever is cheapest to cover, it goes *up* when someone deletes a hard-to-test
module, and once it is on a dashboard the honest answer to "should this `except`
branch have a test?" quietly becomes "will it move the number?".

So `scripts/check_coverage.py` enforces floors per path, each with its
justification written next to it, on the code where an unexecuted line is a
security or correctness risk:

```
app/modules/authz/           100%   the central policy
app/platform/grants.py       100%   media grants and object signatures
app/api/routers/auth.py      100%   sign-in, OTP, session rotation
app/api/routers/platform_ops  95%   takedowns, moderation, seats, payments
app/api/routers/assets.py     95%   the authoring core
app/api/routers/identity.py  100%   profiles, consents, rosters, invites
app/api/routers/speaking.py  100%   age banding, and the one path audio may take
app/api/routers/competitions 100%   the fairness rule, and the ranking students share
app/api/routers/tests_author 100%   composition — the authoring core
app/api/routers/teaching.py  100%   assignments and the regrade flow
app/modules/exam/scoring.py  100%   the server is the sole authority on scoring
app/modules/qtypes/           95%   the three scoring primitives
app/modules/exam/             90%   timing, play-once, submit
app/modules/content/          90%   versioning, publish gate, import
app/platform/                 85%   the kernel
TOTAL                         80%   a tripwire, not a target
```

Each 100 is a 100 *now* — they cost nothing to hold and fail the
moment a new branch lands untested. The global 80 is set far below the actual 96
on purpose: it trips only when something structural breaks, which is a failure
this repository has already had once (`0010` §3.2, "355 passed, 400 skipped",
exit 0).

Both failure modes are verified: raising a floor above reality fails, and so does
a floor whose path has been renamed away — because a floor over zero files always
passes, which is the same shape as the import contract that reported KEPT against
a real violation in `0008`.

### 10.1 What the measurement actually found

The number was never the point. Four things were:

**Eleven decisions in `policy.check` had never executed.** The authorization core
— "enforce centrally, not with scattered role checks". `test_authz_leaks.py`
drives two rival centres through the API and is the more convincing test, but it
only constructs the resources those flows happen to create. Never exercised:
platform-global content being readable, an author reading their own
`author_private` draft, a teacher publishing under `teacher_can_publish`, a
teacher refused an edit to a colleague's work, published content refusing to be
hard-deleted (the branch that keeps takedown evidence alive), and the
`content_grants` clause in `filter_content` — the entire mechanism by which a
paper is deliberately shared with another centre.

`tests/authz/test_policy.py` covers all of them. They are three lines each,
because `check` is a pure function over three fields; reaching them through HTTP
would have needed a fixture per branch, which is why nobody had.

**`verify_object`'s three rejection branches had never run.** It is the only gate
on `dev_storage.py`, which is an *upload* route. The happy path was covered by
the resumable-upload flow and nothing ever presented a bad signature — so the
refusals were unverified on anything booting with `STORAGE_BACKEND=file`.

**`ScoreRun.verdict_of` was dead code.** Defined, never called from `app`,
`tests` or `scripts`. Deleted. Dead code in the scoring engine is worse than dead
code elsewhere: it invites a future caller to use a lookup nothing has exercised.

**And a real crash in scoring.** Chasing the last uncovered line in `scoring.py`
turned up:

```python
"band": float(band_map.band_for(sum(marks))) if band_map else None
```

That guards against a **missing** band map, not against one that returns `None`.
So `float(None)` raised `TypeError` *inside scoring*, and the student's
submission failed rather than their band being absent.

Reaching it needs only an ordinary authoring mistake. A band map is content — a
centre-admin fills in a table of raw ranges — and this runs per SECTION with the
section's raw against the whole-test table. A table that starts at 10, or one
whose `max_raw` no longer matches a paper that has since gained a question, is
enough. A raw score with no band is recoverable: fix the table, regrade, and the
engine is pure so the mark is reproducible. A crash at submit is not.

That is the argument for measuring coverage even while refusing to make it a
target: 87% is not information, but "these eleven authorization decisions have
never run" is. Sections 11-15 are the same exercise applied to one router at a
time, and it held every time.

## 11. The auth router: 59% covered, and an authentication bypass in the gap

`app/api/routers/auth.py` was the largest untested surface named in §10 — 53 of
128 statements, comprising the whole of OTP request, OTP verify, refresh rotation
and Telegram sign-in. It is now 100% and gated there.

Two of the things in the gap were defects a login endpoint cannot have.

### 11.1 POSTing a phone number returned a session for that account

```python
if body.init_data:
    _verify_telegram(body.init_data, settings().jwt_secret)
phone = body.contact_phone
```

`init_data` was **optional**, so verification happened only if the caller chose
to be verified. `POST /auth/telegram/verify {"contact_phone": "+998901112233"}`
returned a working access token for whoever owned that number. Confirmed against
a real database before changing anything: status 200, `access_token` present,
`principal.user.given_name` the victim's.

Not a subtle branch — the main path. A complete account takeover against anyone
whose phone number you knew, and in this product that includes minors.

Two more problems sat behind it:

**The HMAC was verified against `jwt_secret`, not the bot token.** Telegram
derives its key from the bot token; checking a signature with our own secret
validates data we signed ourselves and verifies nothing. There was no
`telegram_bot_token` in config at all.

**`contact_phone` was treated as identity even when `init_data` was present.**
Mini App `initData` does not carry a phone number — it comes from
`requestContact` in the client, and a client can send anything. So a genuine
Telegram account presenting a victim's number was also a takeover, one step
harder.

The fix, which is what the OpenAPI document already described:

* `init_data` is required. `required: [init_data]` was in the schema all along;
  the Pydantic model had it optional.
* Verified against `telegram_bot_token`, and **absent config fails closed** — an
  auth path that degrades to "allow" when a secret is missing is worse than one
  that is switched off, because the missing secret is invisible until someone
  looks.
* `auth_date` must be inside a replay window. Without it a captured initData
  string is a permanent credential.
* Identity is the Telegram user id **inside the signed payload**. `contact_phone`
  may register a new number, never claim an existing one — that answer is
  `phone_already_registered`, and linking is done by SMS code.
* A number registered this way is stored with `phone_verified_at = NULL`.
  Telegram vouched for the Telegram account, not for the phone.

Ten tests fail against the original implementation, which is how the fix was
checked.

### 11.2 The OTP attempt limit could not fire

`otp_verify` checked `attempts >= max_attempts`; nothing anywhere incremented
`attempts`. A challenge accepted unlimited guesses at a six-digit code.

It could not have worked as written. A **wrong** code hashes to a row that does
not exist, so there was nothing to increment — counting matched rows counts only
correct guesses. Worse, `challenge_xid` was never stored: it was generated in
Python, folded into `code_hash = sha256(f"{xid}:{code}")`, and discarded. The
server could not find its own challenge without already knowing the code.

Migration `0020` gives `otp_challenges` an `xid`, and the attempt is now charged
to the challenge **before** the code is compared, which is the only ordering that
costs an attacker something per guess. The practical exposure was bounded —
`challenge_xid` only goes to whoever requested the code — but "the brute-force
guard works as long as nothing leaks" is not a guard, and the code was written as
though it did work.

### 11.3 What else the tests pin

Reuse detection on refresh tokens had no coverage either. It was correct, and it
is the mechanism that turns a stolen refresh token from a 90-day credential into
a one-shot one, so it now has a test that presents a rotated token and asserts
**the whole chain dies** — including the session the legitimate user is holding.
That is the intended, unfriendly behaviour: both parties get logged out, because
the server cannot tell which one is the thief.

## 12. `platform_ops`: 65% covered, and an unauthenticated payment endpoint

The largest remaining gap after §11, and the same story one level worse. 179 of
511 statements unexecuted, two thirds of them the payment callbacks.

### 12.1 `POST /payments/payme` had no authentication at all

Payme authenticates with HTTP Basic — `Paycom:<merchant key>`. The OpenAPI
document has declared `security: [paymeBasic]` since it was written.
`payme_merchant_key` has been in `config.py` since it was written. **Nothing read
it.** The handler took `body: dict` and a session, and that was all.

Verified against a real database before changing anything:

```
POST /api/v1/payments/payme
{"method": "PerformTransaction",
 "params": {"id": "attacker-txn-1", "account": {"order": "ORD-PROBE-1"}}}

-> 200  {"result": {"transaction": "attacker-txn-1", "state": 2}}
   orders.status = 'paid'
```

Anyone who could reach the endpoint and name an order reference got the
entitlement. Free mock exams, free seat licences, and a `payments` table that
disagrees with the provider's — which is the sort of thing you discover during
reconciliation, weeks later, with real money already reported.

Two more holes sat behind it, both reachable the moment the key leaks or the
provider has a bad day:

**`CreateTransaction` never checked the amount.** `CheckPerformTransaction` did.
The provider is supposed to call Check first — but "the other side always calls
the methods in order" is an assumption, and the one that is wrong is the one that
books a 50,000 soum pack for one soum.

**`PerformTransaction` captured transactions that never existed.** It ran
`UPDATE payments ... WHERE provider_txn_id = :txn`, matched zero rows, and then
marked the ORDER paid regardless — an entitlement with no payment row behind it
and nothing for reconciliation to find.

Click was in better shape: it verifies a signature and replays from
`payment_events` rather than re-executing. It had no tests either, and both
providers' secrets defaulted to the literal string `dev-only-change-me` —
**published in this repository**, so a deployment that had not overridden it
accepted a header anyone could compute. Both default to empty now, and empty
means refuse rather than compare.

### 12.2 Two smaller ones, from the same reading

**`common_wrong` counted nothing.** `item-analysis` is documented as how a broken
answer key is found automatically: students who typed something the key rejects.
The SQL was `array_agg(DISTINCT s.raw_response)` and the Python was
`{"count": wrong.count(w)} for w in sorted(set(wrong))[:5]`.

De-duplicated in SQL, so **every count was exactly 1** — "what forty students
wrote" rendered as "what someone once wrote". And `sorted(...)[:5]` is the five
alphabetically-first, so the answer an author opens the page to find could be
missing because it starts with a late letter. Both defeat the only reason the
field exists.

**`POST /admin/lexicon` answered 500 to a typo.** It took `body: dict`, so an
unrecognised `kind` reached the CHECK constraint and came back as an
`IntegrityError` — "Something went wrong on our side" for someone who wrote
`spelling` instead of `spelling_variant`. The aborted transaction then failed
every later query on that session, so by the time anyone looked the real cause
was several errors back. It has a Pydantic model now.

### 12.3 Where it landed

```
platform_ops.py   65%  ->  99%     gated at 95
app/api/routers   77%  ->  84%
repository        88%  ->  90%
```

The seven lines left are the redirect-mode media path, which needs a
`media_delivery=redirect` configuration this suite does not run under. That is
the honest reason the floor is 95 and not 100.

## 13. `assets.py`: the transcript was readable by any student at the centre

The authoring core — the part of the brief that said not to treat this as CRUD
over a questions table — and the last large router at 70%.

Unlike `auth.py` and `platform_ops.py` there was no unauthenticated endpoint
here. There was something narrower and, for an exam product, worse.

### 13.1 The answer sheet, before the exam

`GET /audio-tracks/{xid}/transcript` guarded itself like this:

```python
track = _owned(session, AudioTrack, xid, actor, what="Audio track")
live = ...count attempts where user = actor and status = 'in_progress'...
if live:
    raise Forbidden("... not available while you have a live attempt.")
```

`_owned` with the default `Action.READ` performs **no permission check at all** —
it only scopes the row through `filter_content`, which admits every member of the
owning organization. So any student at the centre could read the transcript of
any listening track that centre owns.

The live-attempt check did not help. It fires only for an attempt already
`in_progress`, so the bypass is the obvious order of operations: read the
transcript, then start the exam. Confirmed against a real database — 200, with
the segments.

The brief's words were "used for post-exam review, **never exposed during the
exam**", and the OpenAPI description says "Authoring and post-exam review only".
Reading it before the exam is not a loophole in that sentence; it is worse than
the case the sentence describes.

It now requires `Action.EDIT` on the track: if you may edit it, you may read its
transcript. The live-attempt check stays as defence in depth for an author
sitting their own paper to check the timing.

**This leaves students with no transcript at all**, and that is worth saying
plainly rather than burying. `GET /attempts/{xid}/review` is the student path and
it needs a scored run — but it does not return transcript segments today, despite
the contract describing them. So post-exam review of listening audio is now
*unimplemented* where it was previously *leaky*. That is the right direction, and
it is in §14.

### 13.2 Both organization settings were dead here

`teacher_can_publish` and `content_edit_others` are the two documented places
where a centre changes what its teachers may do. `policy.check` implements both.
`tests_authoring.py` passes `org_settings` at seven call sites.

`assets.py` passed it at none. So a centre that enabled either found it worked on
a test version and did nothing for the passages, questions and groups inside it.

The direction was safe — too restrictive, never too permissive — which is exactly
why nothing noticed. Wired up now, with a test that turns each setting on and
watches the refusal become an acceptance.

### 13.3 Where it landed

```
assets.py         70%  ->  100%    gated at 95
app/api/routers   84%  ->   88%
repository        90%  ->   92%
```

Four routers read closely now, and the pattern held in all four: **the OpenAPI
document already described the correct behaviour, and the implementation did
something else.** Telegram sign-in, the Payme callback, the OTP attempt limit,
and this. The contract was never the thing that was wrong.

## 14. `identity.py`: the same leak, one endpoint over

The last large router at 70%, and the most instructive of the five — because one
of its two defects had already been found and fixed **in the endpoint next to
it**.

### 14.1 The roster

`GET /cohorts/{xid}/members` was corrected during Deliverable 3 to hand
classmates names only: a `_classmate_dto` with `phone`, `telegram_username` and
`is_minor` nulled out. `GET /orgs/{xid}/members` returns `user_dto` — the full
record — to any member of the organization.

Confirmed against a real database, as the seeded student:

```
student   Aziza     phone=+998948600142  is_minor=False
teacher   Dilnoza   phone=+998996796046  is_minor=False
```

Worse than the one already fixed on both axes: the whole centre rather than one
class, and it includes `is_minor`. A roster of names is a directory. A roster of
names, phone numbers and which of them are children is something else.

Same fix as its sibling: full record for a teaching role, names for everyone
else. The endpoint stays — a student seeing who is at their centre is the point.

The lesson is about how the first fix was made. It was made where the bug was
reported, not across the class of endpoint, and there was no test asserting the
property anywhere else. This one now asserts on the response **text**, so a
future field that happens to carry the number fails too.

### 14.2 An invite you could never accept

`org_memberships` is UNIQUE on `(org_id, user_id)`. `accept_invite` added a
membership unconditionally, so a user already at the centre got an
`IntegrityError` — a 500. And because the failed transaction rolled back, the
invite was never marked accepted: **the same 500 came back on every retry, for
good.**

The realistic case is not exotic. A student is enrolled, the centre starts a
Saturday intensive, the admin sends the class a link for the new cohort. Everyone
already at the centre — which is everyone — hits a 500 they cannot get past.

It is idempotent now, and the role rule needed a decision rather than a default:
**raise a role, never lower one.** The invite names a role and its author holds
`MANAGE_ORG`, so honouring a promotion is the intent — but a centre admin pasting
a `student` link into a group chat must not demote the teacher who clicks it.

### 14.3 What was already right

Worth recording, because four consecutive routers with defects makes it easy to
assume everything is broken. Parental consent is correct and complete:
`stranger_matching` for a minor requires `granted_by_kind == "parent"` **and** a
contact number, the document version and its SHA-256 are stored with the grant,
and an ordinary terms acceptance is still self-service. `date_of_birth` is
genuinely absent from every response and genuinely not editable through
`PATCH /me`. `add_cohort_members` skips duplicates and refuses anyone who is not
already in the organization.

## 15. `speaking.py`: the safety rule holds, the evidence was thrown away

The router I most expected to find a defect in, for the reason given in §14 —
it carries the one rule in the product that is not merely a correctness bug.
**That rule is right.** What was broken is the other half of the same brief
paragraph.

### 15.1 What was already right, in detail

Worth writing out, because "a minor is never matched 1:1 with an adult" is the
constraint the whole product is judged on and this is the first module where the
core requirement is airtight on first reading.

`matching.py` **partitions** candidates on `is_minor` before pairing begins. Not
a filter over a mixed pool — a cross-band pair is not rejected, it is
unreachable. Its docstring says so, and it says the thing I would have gone
looking for next:

> `mixed_supervised` does not weaken it. That band exists so a teacher-run cohort
> session may contain both minors and adults in one ROOM; it does not authorize a
> minor–adult PAIR.

That is the distinction someone gets wrong at 1 a.m. and it is written down. The
HTTP boundary adds two more layers, both correct:

- `list_slots` filters on `age_band` server-side and **`age_band` is not a query
  parameter** — a minor's client cannot ask for adult slots.
- `book_slot` re-checks the band against the acting user's own age, so a client
  that guesses a slot xid still cannot cross it. `mixed_supervised` additionally
  requires cohort membership, which closes the one way an adult could otherwise
  reach a room with children in it.
- A slot's band defaults to **the creator's own band**, not to `adult`. A minor
  teacher who omits the field opens a minor room. A defaulting mistake fails
  closed.

All three layers are now pinned at the HTTP boundary, including the case that
matters most: a minor who has the xid of an adult slot gets 403
`age_band_mismatch`, with a message support can read out loud.

### 15.2 The defect: `has_evidence: true` pointing at nothing

The brief permits exactly one exception to "audio must not transit or be stored
on my servers": *unless required for a safety report.* The safety report was the
case that discarded it.

`report_pair` read the upload, hashed it, recorded `bytes`, `checksum_sha256`
and a `storage_key`, set `speaking_pairs.evidence_media_id`, and returned
`has_evidence: true`. Nothing ever called `storage().put`. Grepping the whole
module for `storage` returned the string zero times.

So the moderator who opens the highest-priority report in the queue — a
`critical` one, because a child is involved — finds a `media_assets` row that is
internally consistent in every field and an object that never existed. There is
no error, no failed upload, nothing in a log. The evidence is simply not there,
and the row asserts that it is.

Two things made it worse than a missing write:

- **The bucket was a literal.** `'safety-evidence'` appears nowhere else in the
  system: not in `config.py` (the bucket is `s3_bucket`, default `ielts-media`),
  not in a migration, not in the docs. `Storage` is single-bucket by
  construction. So even the pointer named a container that has never existed.
- **`file.read()` was unbounded** and the content type came from the client
  unchecked. An authenticated student could send a gigabyte of anything and have
  it read into memory on a 4 vCPU box, and label it `audio/webm`.

Fixed: `_store_evidence` bounds the read at 16 MB (a 60-second Opus buffer is
well under one), refuses an empty buffer and a non-audio content type, calls
`storage().put`, and records `ref.bucket`, `ref.key`, `ref.bytes` and
`ref.checksum_sha256` — the values the store reports, not the values the request
claimed. Status `quarantined` on arrival, as before.

### 15.3 The test that passed against it

There *was* a test. `test_audio_reaches_the_server_only_with_a_report` asserted
that a row existed `WHERE bucket = 'safety-evidence'` and that its status was
`quarantined`. Both were true. It asserted on the invented literal, and it never
looked for the object.

This is the most useful thing in this section. Two of my own replacement tests
had the same shape and I only found out by sabotage:

```
test_the_recorded_size_and_checksum_match_the_object   compared the row to the
                                                       payload the TEST sent
test_the_pair_points_at_it                             asserted the pointer was
                                                       not null
```

Reverting `_store_evidence` to the discard-the-bytes version, one of eight tests
failed. Both of those passed — because both were true of the broken code. The
row was always correct; that was the bug. Rewritten to read the object back out
of storage and derive size and checksum from *that*, the same sabotage fails
three tests. Every guard was then verified the same way: removing the size and
content-type checks fails exactly the three tests that claim to cover them.

A test that reads the database row and stops is not testing that a file was
stored. It is testing that an INSERT ran.

### 15.4 A smaller thing the fix exposed

Once the endpoint actually wrote bytes, the pre-existing test wrote them into
`./var/media/ielts-media/safety/…` — the repository working tree, because
`storage_root` defaults to `./var/media` and that test had never needed a storage
fixture. It now installs a `tmp_path`-rooted `FileStorage`, as
`tests/integration/test_media.py` already did.

`var/` is also in `.gitignore` now, and would have been worth adding regardless:
`FileStorage.__init__` mkdirs its root, so *any* resolution of `storage()` under
the default config creates the directory. Before this change it stayed empty,
which is why nobody noticed.


## 16. `competitions.py`: the fairness rule holds, the ranking did not

The other constraint in this product that is not merely a correctness bug. Same
shape as §15: the load-bearing mechanism is right, and the things standing next to
it were never executed.

### 16.1 What was already right

The two-phase start is correct and the reasoning is written down where the code
is. At T-120s the lobby serves the payload **AES-GCM encrypted**, with a
per-client jitter derived deterministically from `(competition_xid, user_id)` so a
retry lands in the same slot rather than re-rolling onto the spike it was
avoiding. At T-0 the client fetches ~100 bytes of key. The encryption is not
theatre: an unencrypted payload sitting on a device from T-120s is a two-minute
reading head start for anyone who opens devtools, and a test asserts the passage
title is absent from the ciphertext.

The clock is server-authoritative in the way that matters. `release_key` sets
`started_at = row["starts_at"]`, not `now()`, and
`expires_at = min(starts_at + duration, ends_at)`. A student on a slow connection
who asks three seconds late does not get three extra seconds, and one who asks
early does not start early.

The payload key is **derived**, `sha256(jwt_secret : payload : key_id)`, not
stored — so the key for a contest that has not started exists nowhere at rest.

`_freeze_keys` is the enforcement behind "a key fix cannot silently re-rank a
finished contest": the contest records which answer-key versions it was scored
against, so a later fix is visibly a *different* set of inputs and needs a
decision. It is now pinned that the freeze happens once per **contest**, not once
per student — otherwise `frozen_at` drifts with the slowest connection in the
room.

### 16.2 A capacity-capped contest could not be entered at all

```python
taken = session.scalar(text("""
    SELECT count(*) FROM competition_entries
    WHERE competition_id = :c AND status <> 'withdrawn' FOR UPDATE
"""))
```

PostgreSQL refuses this outright:

```
ERROR:  FOR UPDATE is not allowed with aggregate functions
```

So `max_participants` was not merely unenforced — **every registration for a
capped contest returned 500.** A centre that caps a contest at 30 seats has an
endpoint that does not work, and the three lines involved had never been executed
by any test.

The lock it was reaching for would not have worked either. Locking the entry rows
that already exist cannot stop a concurrent `INSERT` of a new one, so the comment
above it — "two simultaneous registrations for the last place cannot both
succeed" — was false on its own terms. The fix locks the **competition** row,
which is the thing both transactions have in common.

### 16.3 The leaderboard ignored the contest's own tiebreak

`tiebreak` is a per-contest jsonb array, and the schema says why: "data rather
than code so a centre can run 'highest score, then fastest' without a deploy".
`materialize()` honours it via `ranking.rank()`. The display query did not:

```sql
ORDER BY r.raw_score DESC, r.duration_ms ASC, r.submitted_at ASC
```

Hardcoded to the default rules, and ignoring the `rank` column it was selecting
and returning. `band_desc` is a supported rule with no term in that ORDER BY at
all, so a contest configured `["band_desc", "duration_asc"]` returned rank numbers
that contradicted the order of the rows they were printed beside. Under `LIMIT`
it is worse than confusing: the ordering cuts from the wrong end, so **the actual
winner can be missing from the top of their own board.**

The hardcoding was not arbitrary — the migration adds
`competition_results_board_idx` on exactly those three columns, commented "so the
leaderboard is a plain index scan with no sort node". But there is also
`competition_results_rank_idx ON (competition_id, rank)`, and `rank` already
encodes whatever tiebreak the contest chose. Ordering by `rank` is correct *and*
an index scan, so honouring the contest costs nothing. Ties still share a rank —
"inventing a winner between two identical papers is the one thing a leaderboard
must never do" — with the board index as the deterministic order inside a shared
rank, and `NULLS LAST` so an unranked row cannot float to the top.

### 16.4 `around_me` did nothing, and there was no `ETag`

Both are in the OpenAPI document. Neither was in the code.

`around_me: bool = False` was accepted by the handler and never read. A student
ranked 340th of 500 got rows 1-25 and their own number, with no way to see their
neighbourhood — which for roughly 95% of a field is the only view worth having.
It now windows on the viewer's own position, in the same query, with a fallback to
the top for someone who did not sit the contest.

The spec is more pointed about the missing `ETag`. It documents the header on
every response and a `'304': Unchanged`, and describes this endpoint as "the
fallback for clients that cannot keep a socket open, **which on these networks is
a meaningful fraction**". Every one of those clients re-downloaded the whole board
on every poll. Five other endpoints in this codebase set an `ETag`; this one did
not, and nothing anywhere returned a 304.

The tag is a hash of the **body**, not of `max(computed_at)`, for two reasons: it
has to distinguish views as well as versions, or a client switching between the
top and its neighbourhood is served the other one's 304; and `generated_at` has
to be excluded, or a provisional board mints a new tag on every poll — precisely
the case the tag exists to serve. The saving is the transfer rather than the
query, which is the right way round on a mobile network.

One smaller divergence, fixed in passing: `limit` defaulted to 50 and clamped at
200, where the spec's shared `Limit` parameter says default 25, maximum 100. The
spec is the contract clients are written against.

## 17. `tests_authoring.py`: composition, and the two faults that reach a student

The assembly half of the authoring system — 466 statements, the largest untested
surface left, and the part of the product the brief calls the core. Three faults,
and unlike §§11-16 two of them are not information leaks or refused requests:
they are a broken exam and an unpublishable test.

### 17.1 A section could not be moved

`update_section` had never been executed by any test. Both directions were broken.

`_make_room()` is *insert* semantics: park every row at or after the target in the
negative range, then bring them all back one higher. Its docstring explains why
the two-step shift is needed — `(test_version_id, position)` is a plain UNIQUE
index, so a single `SET position = position + 1` collides with a row it has not
moved yet — and it is right about that.

`update_section` parked the moving row itself first, then called it. The second
statement is `WHERE position < 0`, so it swept the mover up with everything else:

```
sections 1, 2, 3 — move section 1 to position 3
park            -1,  2,  3
_make_room(3)   -1,  2, -3
step two         2,  2,  4     ERROR:  duplicate key value violates unique
                               constraint "test_version_sections_pos_uq"
```

A 500 on every downhill move, reproduced at the SQL level before anything else.

Uphill was worse, because it succeeded. `_make_room` shifted rows that should not
have moved, leaving **1, 2, 4** — and nothing downstream complains. The publish
gate did not check contiguity. But `ExamSession.start` copies each section's
position onto the attempt:

```python
self._s.add(AttemptSection(attempt_id=attempt.id, section_id=s.id,
                           position=s.position))
```

and `enter_section(attempt, position)` looks it up by that number. So an author
reorders a paper on Tuesday, it publishes cleanly, and on Friday a cohort reaches
the end of section 2, asks for section 3, and gets **"Section not found in this
attempt"** — in a timed exam, with no way forward and no way to tell them why.

A move is not an insert: only the span the section travels over shifts, and it
shifts *towards* the vacated slot. `_move_section` does that, excludes the parked
mover from the shift, and clamps the target to the section count so "move to
position 99" means "move to the end" rather than leaving a permanent gap at 4-98.
`create_section` clamps the same way and `delete_section` closes the hole it
leaves, because a gap from a delete reaches a student exactly like a gap from a
move.

Then the same rule in the gate, since the gate is the last thing between a stored
version and a cohort sitting it, and "this section is unanswerable" is the class
of fault it exists to catch:

```
SECTION_POSITION_GAP  Section positions are [1, 2, 4], which is not 1-3.
                      Missing: [3].
```

**One of my own tests was too weak and only sabotage found it.** The first version
of "moving earlier leaves no gap" moved the *last* section to the front — which
survives the old code, because `_make_room` sweeps every row including the parked
mover and the mover's position is then overwritten anyway. Moving a *middle*
section is the case that leaks the gap. Same lesson as §15.3: the test that
happens to pass is not the test you wanted.

### 17.2 No test could be published through the API at all

`band_map_versions` was the one table in this system that never got an `xid`. Every
other public identifier is an opaque UUIDv7 over a bigint primary key. The two
endpoints that expose a band-map version papered over the gap:

```python
"current_version": {"xid": str(current.id), ...}
```

`GET /band-maps` handed a client `"7"` and called it an xid. That is the internal
id on the public surface — the thing the whole scheme exists to prevent, and a row
count a competitor can read off a response.

It also shut the only door for attaching one. `PATCH /test-versions/{xid}` takes
`band_map_version_xid: uuid.UUID` and resolved it with `BandMapVersion.xid == ...`,
an attribute the model did not have. So the `"7"` the API had just handed out was
rejected by request validation as not-a-uuid, and a real uuid raised
`AttributeError` — a 500. Both directions closed.

That is not an endpoint nobody uses. `publish_gate` refuses a version with no band
map (`BAND_MAP_MISSING` — "without a band map a score is a raw count, which is not
what a student or a centre asked for"), so **a centre could not publish anything
through the API.** Migration `0021` adds the column, the model maps it, both
endpoints emit the real xid, and a test walks the whole round trip: create a band
map, read the version xid the API returns, attach it, confirm it landed.

`tv_dto` also had `"band_map_version_xid": None` hardcoded, so a version never
reported which band map it was scored against — leaving "why won't this publish?"
unanswerable from the API even once the attach worked.

Why 1316 tests missed it: the fixtures set `band_map_version_id` in Python.
`/band-maps` was reached only by the authz leak sweep, which collects every key
ending in `xid` and checks none belongs to a rival — and `"7"` never matches a
uuid, so it passed. Covered, and never verified.

### 17.3 The library never said whose paper it was

`org` is declared on the spec's `Test` schema. `test_dto` emitted no such field,
so the authoring library returned rows with no attribution — which for a platform
admin looking at every centre's material at once is the one thing they need.

Added as identity only: `xid`, `name`, `slug`, `kind`, `status`. Deliberately
*not* `identity.org_dto`, which also returns `settings` — a `platform_global` paper
shared by one centre appears in another centre's library, and emitting its owner's
configuration there would hand a competitor how that centre is set up.

That distinction needed a decision rather than a default, and it is now a test
with its reasoning in the docstring: **attribution travels with content the viewer
is already entitled to see.** Every route by which centre B sees centre A's test is
a deliberate act — A set it `platform_global`, A issued a `content_grant`, or a
platform admin is looking — and in all three "this paper came from Tashkent Prep"
is the expected behaviour of shared material, not a leak of it. The half that is
not negotiable is pinned alongside it: an org-private paper is still invisible to
a rival, listing and all.

### 17.4 What was already right

`_renumber` is correct and its comments explain the two things that are easy to
get wrong: `rows` has one entry per item so only the first sets `number_start`, and
a question consumes one number *per slot* — a three-blank sentence completion is
questions 14, 15 and 16. `_passage_ref` and `_audio_ref` resolve through the
actor's own scope, so a reference cannot smuggle a competitor's passage into a test
you own; both doors are now tested, POST and PATCH. Visibility widening correctly
requires `Action.SHARE`, which is centre-admin-only, so a teacher cannot publish
their centre's material to the platform. And the cross-org clone genuinely needs a
`copy` grant: a `view` grant is not enough, and revoked and expired grants are
both refused.

```

app/api/routers      95%  ->   97%
repository           94%  ->   95%   (71 new tests, 1316 total)
```

## 18. `teaching.py`: the last router, and two things a centre would have hit
    in week one

Assignments and the regrade flow — what a teacher does once the authoring is
done. The last router under 90%, and the gap held two defects that are not
subtle: one refuses a teacher permission to do their job, the other lies to them
about the blast radius of a regrade.

### 18.1 A teacher could not assign to their own student

`target_kind="users"` is the ad-hoc path — name three students and set them work.
It exists precisely for the case a cohort assignment does not cover. Its "is this
student at my centre?" check was:

```python
members = set(session.scalars(
    select(CohortMember.user_id)
    .join(Cohort, Cohort.id == CohortMember.cohort_id)
    .where(CohortMember.user_id.in_(ids),
           Cohort.org_id.in_(actor.org_ids or [0]))))
if set(ids) - members:
    raise Forbidden("You can only assign to students in your own centre.")
```

A centre's roster is `org_memberships`. `cohort_members` is who is in a *class*.
So a student enrolled at the centre but not yet in any class — which is every
student on their first day, and the exact case this target kind exists for — was
refused with a message telling them they are not at the centre they are at.

It was also wrong in the other direction. Cohort rows outlive enrolment: a student
who left in June commonly still has last term's class row, and that stale row was
enough to keep setting them work in September. The test pins both halves, and the
departed-student case is the one that only sabotage caught — my first version of
it did not leave the student in a cohort, so it passed against the bug.

`identity.add_cohort_members` already asks this question correctly, one file over,
`status = 'active'` and `left_at IS NULL` and all. Same shape now.

There was also a dead query immediately above it — `outside` was computed, assigned
to `_`, and discarded, with a comment explaining that it did not matter. Deleted.

### 18.2 A band-map regrade reported an impact of zero

The regrade flow is deliberately three steps, and the middle one is the point:

```
stage (dry run)  →  read the impact  →  apply
```

`_affected_count` is what fills in "the number the author actually wants first:
how many students does this touch". It had branches for `question_version`,
`test_version` and `attempt`, no branch for `band_map_version`, and a bare
`return 0` at the end to fall into.

A band map is the curve every test version using it is scored against, so retuning
one is the widest-reaching regrade in the system — and the number in front of the
person deciding whether to run it was **0**. The job itself was real:
`exam.planner` scopes `band_map_version` perfectly well. Only the impact estimate
was missing, which is the worst place for it to be missing, because 0 reads as
"this is a no-op, go ahead".

Now counted, scoped exactly as the planner scopes the job — attempts on test
versions using that band map, excluding previews and unfinished papers. A count
that disagreed with the plan would be worse than none.

The trailing `return 0` is gone. All four subject types in
`RegradeCreate.subject_type` are handled, so the fall-through now raises: a silent
zero is precisely how this defect existed, and the next person to widen that
pattern should hear about it rather than ship another lie.

### 18.3 What was already right

The competition guard on `apply` is correct and is now pinned: a regrade that
would move a finished contest's ranking is refused with the list of contests, so
the admin knows what to go and decide rather than being told "no". A recorded
decision unblocks it; an impact marked `decision_required: false` never blocked it.
`assignment_progress` needs a *teaching role* at the centre that set the work —
org membership is not enough, and a classmate gets a 404, which is right because
that response carries every student's live progress, band and phone number. And
the assignment audience is materialized at creation, so a student who joins the
cohort next week is not silently late for work set before they arrived.

```
teaching.py       83%  ->  100%
app/api/routers   97%  ->   99%
repository        95%  ->   96%   (66 new tests, 1382 total)
```

Six routers are now at 100% and `platform_ops` at 99%. **Every one of the seven
largest had at least one defect in the part no test executed** — that is the
finding this exercise produced, and §0 states it as a table rather than a number.
What is left is `authoring.py` (95%), `exam.py` (89%) and `dev_storage.py` (71%,
and dev-only).

## 19. Still open

1. **Actions are pinned by major tag, not by commit SHA.** `actions/checkout@v4`
   is a moving reference; the hardening is to pin the 40-character SHA. I did not
   do it here because I could not read the SHAs — this environment's GitHub
   access is scoped to this repository — and a SHA written from memory is a
   pipeline that cannot start. `.github/dependabot.yml` now watches
   `github-actions` monthly, which surfaces a `v5` as a pull request; pinning is
   a five-minute job for anyone who can open github.com.

2. **Students cannot see a listening transcript at all.** Closing §13.1 removed
   the only path they had, and it was the wrong one. `GET /attempts/{xid}/review`
   is the right one — it needs a scored run, so it is safe by construction — and
   the OpenAPI document already describes it returning transcript segments with
   an audio timestamp range. `ExamSession.review()` does not return them. That is
   the next feature, not the next test.

3. **`app/api/routers` is at 99%.** Nine routers are done. What is left is
   `authoring.py` (95%), `exam.py` (89%) and `dev_storage.py` (71%, dev-only and
   never deployed). `exam.py` is the one worth reading next — it is the student's
   side of the timing authority and play-once, and the only large surface left
   that a student touches directly.

   Nine routers read closely, nine with at least one defect where the contract and
   the code disagreed. That is not a coincidence and it is the single most useful
   thing this exercise has produced: **the OpenAPI document is a more accurate
   description of this system than the code is.** Anywhere the two disagree, the
   document has so far been right.

   Below the routers: `app/modules/competitions/service.py` is at 80% — the
   `republish` path, i.e. the code that actually rewrites a published ranking
   after a decision. That is the other half of §16 and it deserves the same
   treatment. `app/modules/speaking/service.py` is at 91% and `matching.py` at
   97%; the matcher is the layer the brief actually names ("enforce age banding at
   the matching layer") and its three uncovered lines are worth closing on that
   basis alone.

4. **Content review is optional, in the spec as well as the code.**
   `submit-review` and `review` exist and work, and `decide_review` correctly needs
   PUBLISH authority so a teacher cannot approve their own work. But
   `publish_version` never looks at `content_reviews`: a centre admin can publish a
   draft that was never reviewed, and can publish one that was approved and then
   edited afterwards, since `approved` leaves the version editable. `test_versions`
   has no `approved` status to move it to — the CHECK constraint allows only
   `draft|in_review|published|archived` — so the code's choice is forced, and it
   says so. Whether a centre should be able to require review before publish is a
   product decision, not a defect; if the answer is yes it wants an org setting, a
   fifth status, and a check in `publish_version`.

5. **An invite is not bound to the phone it was addressed to.** `create_invite`
   takes a `phone` and stores it; `accept_invite` never looks at it, so whoever
   holds the token takes the role. That is defensible — the token is the
   credential, and a centre admin pasting a link into a class group chat is the
   intended flow — but it means a forwarded link is a transferable role, and a
   `centre_admin` invite is worth forwarding.

6. **Three endpoints still take `body: dict`** — `create_block`,
   `take_moderation_action`, `decide_takedown` — which is what made the lexicon
   endpoint answer 500 to a typo (§12.2). They are admin-only, so the blast
   radius is small, but the fix is a Pydantic model each.

7. **Import sorting is off**, as above: 31 files, one `--fix`.

8. **The suite emits ~1200 warnings** and CI reads none of them. Among them is
   `InsecureKeyLengthWarning: The HMAC key is 18 bytes long, below the minimum
   recommended 32` — from the test JWT secret, so harmless here, but exactly the
   kind of thing that should be `-W error` for a chosen list rather than scrolled
   past. A deprecation that is a warning today is a failure on some future
   dependency bump, and finding out at upgrade time is finding out late.

9. **The smoke test covers one actor.** It proves the broker binding, the relay
   and the worker loop, which is the mechanism — but `deliver_notifications` is
   the only actor it actually runs. `ingest_audio` is the one whose failure is
   expensive and whose dependencies are heaviest (ffmpeg in a worker process, not
   in pytest), and it is the obvious second job to add.

10. **The relay is not run as a process anywhere.** `make smoke` calls
   `relay.drain()` in-process. The deployed relay is a loop in its own container
   with its own restart policy, and nothing exercises that loop — only the
   function inside it.
